# Trato

**Trato hecho. Say it, get it approved, get paid.**

Trato is a tiny contractor workflow: record or type scope changes, send clients a no-login approval link, then invoice exactly the approved total through PayPal Sandbox. Evidence is preserved as event transcripts. Paid state comes only from confirmed PayPal invoice status.

## Quick start

```bash
npm install
cp .env.example .env
npm run dev
```

Open `http://localhost:5173`.

Production-like single-process run:

```bash
npm run build
npm start
```

## Environment variables

See `.env.example`.

- In development, the app runs in degraded mode when optional AI/PayPal credentials are absent.
- In production, required secrets are validated at startup and the process fails fast if missing.

## PayPal Sandbox setup

1. In PayPal Developer Dashboard, create a REST app and copy Sandbox `client id` and `secret`.
2. Create one Sandbox **business** account (contractor/invoicer) and one Sandbox **personal** account (payer).
3. Configure webhook URL: `PUBLIC_BASE_URL/api/webhooks/paypal`.
4. Subscribe to invoice-paid events (for example `INVOICING.INVOICE.PAID`) and copy the webhook ID to `PAYPAL_WEBHOOK_ID`.
5. Set `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID` and keep `PAYPAL_BASE_URL=https://api-m.sandbox.paypal.com`.

## Render deploy (single service)

1. Push this repository.
2. Create one Render Web Service from the repo.
3. Render uses `render.yaml`:
   - Build: `npm ci && npm run build`
   - Start: `npm start`
4. When Render prompts for Blueprint environment variables, enter:
   - `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` from the Turso database.
   - `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, and `PAYPAL_WEBHOOK_ID` from PayPal Sandbox.
   - `PUBLIC_BASE_URL` as the deployed service URL, such as `https://trato.onrender.com`.
5. Render generates `JWT_SECRET` automatically. Keep `NODE_ENV=production` and
   `PAYPAL_BASE_URL=https://api-m.sandbox.paypal.com`.

If the Web Service already exists, add the same variables under Render's
Environment settings before redeploying. Do not commit these values to the
repository.

## How PayPal is used (hackathon summary)

- Trato creates one invoice per job from deterministic backend totals (original quote + approved changes only).
- Invoice creation/sending uses PayPal REST invoicing endpoints.
- Webhooks and manual refresh are only triggers; paid status is written only after direct `GET /v2/invoicing/invoices/{id}` confirms `PAID`.
- Mock mode (`PAYPAL_MOCK=true` in non-production) keeps demo flow usable without PayPal credentials.

## How AI is used (hackathon summary)

- Voice audio can be transcribed via ElevenLabs STT.
- Transcript extraction via Groq only drafts form fields (`description`, `amount`, `currency`, `days_delta`).
- AI never writes events, computes totals, creates invoices, or marks payments paid.
- If AI is unavailable, typed/manual flow still works.

## Trust rules summary

1. Proposed changes are separate from approved changes.
2. AI drafts; humans decide.
3. Money storage and settlement are integer USD cents.
4. `job_events` is append-only and all state is derived.
5. Transcripts are retained as evidence on change events.
6. Disputes remain visible.
7. Paid state requires PayPal invoice confirmation.
8. Client token links authorize one job and limited client actions.
9. Audio is never stored.
10. If AI/FX fail, typed USD entry still works.

## Assumptions

- `GROQ_MODEL` defaults to `llama-3.1-8b-instant` when omitted.
- Currency selector is intentionally short (`USD`, `ZAR`, `EUR`, `GBP`) to keep UI minimal.
- Exchange-rate previews and server conversions use Frankfurter latest endpoint with 1-hour in-memory cache.
- The app stores timestamps in ISO strings (UTC) generated by the server.
- PayPal webhook signature verification runs only when PayPal credentials are configured (or mock mode in non-production).

## Known limitations

- Single invoice per job.
- USD-only settlement and storage (non-USD only at entry/conversion time).
- PayPal Sandbox-focused implementation.
